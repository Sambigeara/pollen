Troubleshoot

Common symptoms with their likely causes and the fix. Use the symptom you actually see as the lookup key. If nothing here matches, the daemon log is the next place to look. pln logs -f follows it live.

Before you dig in

Three commands will tell you most of what you need to know:

pln status # peers, services, seeds, sites, blobs at a glance pln logs -f -n 200 # tail the daemon log; ctrl-c to exit pln version # confirm the binary you have

If pln status errors immediately, the daemon isn't running. Skip to Daemon won't start or isn't reachable.

macOS: sendmsg: no route to host on LAN dials

Symptom. Calls to peers on the same network silently fail or surface EHOSTUNREACH. Internet peers work fine. Restarting the daemon doesn't help.

Cause. macOS Local Network Privacy is denying pln access to the LAN. The first time the binary tries to reach a LAN peer, macOS prompts; if you missed the prompt, or the binary's signature changed (after an upgrade or ad-hoc resign), the privilege is revoked silently.

Fix. Grant access in System Settings → Privacy & Security → Local Network, then restart the daemon:

pln restart

If pln isn't listed, force the prompt by running pln status while a LAN peer is up.

Linux: permission denied on the daemon socket

Symptom.

Error: cannot reach daemon — are you in the pln group? fix: sudo usermod -aG pln $(whoami) && newgrp pln

Cause. The system daemon runs as the pln user and the socket is group-owned by pln. Your shell user isn't in the group yet.

Fix. The installer adds you to the group automatically when run with sudo. If something went sideways:

sudo usermod -aG pln "$USER"

Open a new shell for the change to take effect (or newgrp pln in the current one).

Daemon won't start or isn't reachable

Symptom.

Error: daemon is not running

or the daemon flips to failed in brew services / systemctl status pln.

Cause(s). One of:

  • Port already in use. Another process holds UDP 60611 (default).
  • State directory unwritable. Ownership of ~/.pln or /var/lib/pln got out of sync after a manual file copy or a failed install.
  • Grant past its deadline (degraded mode). The daemon starts but logs node grant no longer valid — starting in degraded mode and refuses some operations until it can rejoin.

Fix. Check the log first:

pln logs -n 200

For port collisions, change the listening port: pln up --port 60612 (foreground) or edit the service unit. For ownership, run sudo chown -R pln:pln /var/lib/pln on Linux. For a grant past its deadline, see Access expired or node degraded.

A peer shows offline that should be online

Symptom.

pln status nodes offline peers: 1 (use --include-offline)

Cause(s).

  • Daemon down on the peer. The mesh marks unreachable peers offline after a short grace period.
  • NAT punching failed and there's no relay. The two peers can't find a direct path and can't relay either.
  • Firewall. A new outbound rule blocks UDP 60611 in either direction.

Fix. SSH to the peer and check pln status there. If the daemon is up but isolated, add a relay (recipe) so peers behind NAT can fall back to it. For firewalls, allow outbound UDP on the configured port (default 60611) and any other ports the relay uses.

Seed never reaches its target replica count

Symptom.

pln status seeds SEEDS NAME HASH STATUS REPLICAS LOCAL UPTIME hello 4f3a7c91 unknown 0/2 - 30s

Cause(s).

  • No node has capacity. The scoring round didn't find a candidate. Add a node, or raise the per-workload limits (--memory, --timeout) to fit on what you have.
  • Artefact hasn't replicated yet. A scheduled host is still pulling the WASM bytes. Watch pln status blobs to confirm the hash is reaching new nodes.
  • Spec policy excludes every node from acting on it. Rare, but possible if you used --allow-prop on a workload such that no node-side identity matches.

Fix. Watch the daemon log on the candidate hosts (pln logs -f on each). The supervisor logs scoring decisions and any failures (CAS pull errors, validation failures).

pln seed --allow-prop is refused with publish denied

Symptom. A publish carrying an --allow-prop clause is refused and the CLI prints why:

pln seed ./hello.wasm --allow-prop role=admin Error: publish denied: local grant is missing prop "role" (policy requires "admin")

Cause. The publish was rejected at the admission authorise stage. Hosting a workload includes loopback invocation, so a node must satisfy the policy clause it attaches to its own spec. If the publishing node's grant does not carry the property the --allow-prop clause requires, the spec is rejected up front rather than left orphaned in gossip. This is the local publisher acting on its own grant, so the reason is returned in full; a remote caller denied by the same clause sees an opaque not-found instead (see Call returns no such workload). It is also distinct from the authenticate stage, where an invalid session fails first (see Access expired or node degraded).

Fix. Have an admin add the missing property to the publisher's grant, or relax the clause by re-publishing without it:

pln grant <publisher-peer> --prop role=admin # from an admin shell pln seed ./hello.wasm --allow-prop role=admin

See Authorisation for why hosts are gated alongside callers.

pln grant succeeds but the peer still shows the old tier

Symptom. An admin runs pln grant peer --admin and gets upgraded ... → admin, but the peer's own pln status still projects a leaf view and lists only its own resources.

Cause. The push reached the peer's daemon, was verified, and was adopted into in-memory credentials, but a wire-mode client on the peer's side is still authenticating with a session minted from the old grant cached in the TLS extension. Sessions self-mint from the current grant on next refresh; the in-flight session keeps the old view for its remaining lifetime.

Fix. Wait for the next session refresh, or force a fresh dial:

pln status # after a short delay, reflects the new tier

pln grant prints a token instead of upgraded …

Symptom. An admin runs pln grant peer --admin and instead of upgraded peer → admin the CLI prints a long base64 string to stdout with a stderr line:

pln grant 44a13d80 --publisher pln: 44a13d80 has no live mesh daemon; deliver this token and have 44a13d80 run `pln join` Csm…<base64 invite ticket>…

Cause. The target is a wire-mode tenant with no daemon for the admin to push to, so pln grant falls back to minting a subject-pinned invite ticket. The tenant has to redeem it themselves; the admin cannot complete the swap on the tenant's behalf because only the tenant holds the signing key the cluster CRDT requires for the new grant.

Fix. Hand the token to the tenant (a pasted SSH command works fine) and run pln join <token> on the tenant's host. pln join verifies the token, swaps the on-disk grant in place, and preserves the tenant's existing signing key so their identity is unchanged. See pln grant.

pln fetch fails with no publisher known for blob

Symptom.

pln fetch ab12cd34 ./out.bin Error: no publisher known for blob

Cause. Fetch always streams from the blob's publisher. If the blob has no BlobSpec in gossip (an orphan, or a digest you typed wrong) there is no origin to talk to.

Fix. List the blobs the cluster knows about and pick a name or matching digest:

pln status

pln fetch fails with open stream to publisher ... failed

Symptom. A one-shot pln fetch returns an error referencing the publisher's short peer ID. A blob, site or workload that was seeded (replicated across the mesh) keeps serving even while its publisher is offline.

Cause. pln fetch streams directly from the blob's origin and does not fall back to other holders, so it fails if the publisher is offline, partitioned, or behind NAT the mesh has not punched yet. A seeded artefact is different: replicas already hold the bytes and keep serving while the publisher's grant is within its deadline and not revoked. It only stops being admitted by new or restarted nodes once that grant has expired or the publisher's identity was denied (see A site or blob keeps fewer replicas than expected).

Fix. Confirm the publisher is online in pln status. For content you need retrievable without the origin, do not rely on pln fetch; seed it so replicas hold it:

pln seed ab12cd34 myblob # pin a named, replicated copy

A seeded copy survives the original publisher going offline; a bare pln fetch does not. See pln seed.

Call returns no such workload

Symptom.

pln call greeter run 'hi' Error: no such workload

Cause. The target could not be resolved on any reachable node. A caller denied at the authorise stage sees the same opaque answer as a genuinely absent workload: the authorise stage evaluates the resource's --allow-prop clauses against the caller's authority, and a failed match is reported as not found rather than as a distinct denial, so an unauthorised caller cannot probe for which workloads exist. If the session itself were invalid the call would fail to authenticate first instead (see Access expired or node degraded).

Fix. Inspect the spec and the caller's authority:

pln status seeds --wide # shows policy on the spec pln inspect $(pln id) # shows your tier and attributes

Then either have an admin add the missing property to your grant (pln grant <your-peer> --prop key=value) or relax the spec by re-publishing without the offending clause.

Publish refused with budget exhausted or lacks publish capability

Symptom. A publish is refused and the CLI prints the admission reason:

pln seed ./hello.wasm hello Error: admission: functions budget exhausted: authority holds 5, limit 5

A static site or a blob over its cap is refused the same way, with its own kind token (sites or blobs).

Cause. The write was rejected at the admission account or authorise stage. That verdict is returned to the publisher as a failed precondition, so the reason is on the CLI; the same line is also recorded in the daemon log. It is one of:

  • admission: functions budget exhausted: authority holds 5, limit 5: the count budget for that kind is full. The kind token is plural (functions, blobs or sites).
  • admission: authority grant lacks publish capability for functions: the grant was never given the right to publish that kind, so no budget applies.

Fix. For an exhausted budget, unseed something of that kind to free a slot, or have an admin raise the limit, either on a connected peer or at enrolment:

pln grant <peer-id> --max-functions 20 # or --max-blobs / --max-sites pln invite --publisher --max-functions 20 # same flags at enrolment

For a missing capability, an admin must re-grant the peer at a tier that may publish that kind:

pln grant <peer-id> --publisher

See Admission for how the account and authorise stages check budgets and capability.

Wire command fails with out of date

Symptom. Exactly one of:

pln status pln is out of date: this daemon speaks protocol 1-3 but pln supports only up to 2; upgrade pln
the daemon is out of date: it speaks protocol 1-2 but pln requires at least 3; upgrade the daemon
the daemon is out of date: it does not support protocol negotiation; upgrade the daemon

Cause. A wire client and the daemon it connects to negotiate a protocol version. These messages mean the two supported ranges do not overlap, so the older side cannot speak the newer side's protocol.

Fix. Upgrade whichever side the message names. If it says upgrade pln, update the local CLI; if it says upgrade the daemon, update the remote host's binary and restart it:

pln upgrade # local CLI ssh edge.example.com 'pln upgrade && pln restart' # remote daemon

Keep client and daemon on close versions to avoid the gap reopening. See Versioned wire.

Access expired or node degraded

Symptom. The pln status footer prints a single line for a grant that has a deadline (a delegated leaf or publisher grant). While the grant is valid it reads temporary access expires in 2d; once the deadline passes it becomes temporary access expired — rejoin the cluster or contact a cluster admin:

pln status temporary access expired — rejoin the cluster or contact a cluster admin

A daemon restarted while the grant was already past its deadline logs:

node grant no longer valid — starting in degraded mode; rejoin with `pln join <token>`

In wire mode the failing command itself diagnoses it: an opaque dial error is turned into an actionable two-line message on stderr.

pln --context staging status cannot reach pln://staging.example.com: unavailable: remote error: tls: bad certificate context grant deadline passed at 14 May 2026 22:25 BST; rejoin with `pln join <token>` (mint one on the cluster with `pln invite`)

The indented second line is the actionable part and varies with the cause: this context's identity has been denied by the cluster; you need a fresh `pln join <token>`, or context grant no longer validates against the stored root (the cluster was likely re-rooted); rejoin with a fresh `pln join <token>`, or no credentials in this context; run `pln join <token>` first. The bare transport error before diagnosis is usually tls: bad certificate: the session no longer authenticates because the underlying grant is no longer valid; the endpoint itself is reachable. pln context show reports the same state structurally as status: expired or status: revoked (see Recover a context that can't connect).

Cause. A delegated grant has one hard deadline (default 30 days) fixed when it is first issued. Renewal is automatic and happens in the background against any reachable delegating peer, so this state is only reached after prolonged isolation: the node could not reach any delegating peer for the entire renewal window, or its identity was denied by the cluster, or the cluster was re-rooted so the grant no longer validates against the stored root. Admin and infra grants carry no deadline and are unaffected.

Distinguish the two states. Degraded means the node is still serving on a valid-but-expiring grant whose renewal keeps failing; you have until the deadline to restore connectivity to a delegating peer and let renewal succeed on its own. Expired means the deadline has passed: the node has stopped, no further renewal is possible, and it must rejoin with a fresh grant.

Fix. There is no pln renew; renewal is automatic and only fails after the node has been cut off for the whole renewal window. If the node is degraded, restore its path to a delegating peer (see A peer shows offline that should be online) and renewal recovers on its own before the deadline. If the deadline has already passed, or the identity was denied, or the cluster was re-rooted, mint a fresh invite on an admin and rejoin:

ssh admin.example.com pln invite --ttl 24h pln --context staging join <token>

See Sessions for how automatic renewal works and Grants for the deadline.

A site or blob keeps fewer replicas than expected

Symptom. A static site or named blob shows fewer claimants than its serving capacity, and a restarted or freshly joined node never picks up a copy:

pln status STATIC NAME MANIFEST REPLICAS LOCAL PUBLISHER docs 9f3a1c20 1/2 7c4d8e10

Cause. A spec travels with the publisher's grant. A node admits it from gossip only while that grant is within its deadline and the publisher's identity is not denied. Once the publisher's grant passes its deadline, or the identity is denied, a restarted or freshly joined node refuses the spec and will not claim a replica. A node already holding it keeps serving from its own slot, so the site or blob stays reachable at reduced replication rather than disappearing. See Grants for the deadline.

Fix. Rejoin the publishing context and re-publish so the spec travels under a current grant. Check where that context stands first:

pln --context staging context show context: staging target: root@staging.example.com dir: ~/.pln/contexts/staging identity: ab12cd34 issuer: 7c9a4f02 status: expired not before: 14 Apr 2026 22:25 BST rejoin by: 14 May 2026 22:25 BST caps: delegate=false admit=false publish=true max_depth=0

If the grant deadline has passed or the identity was denied, rejoin (see Access expired or node degraded), then publish the same source under the same name:

pln --context staging seed ./public docs

Replication returns to capacity as nodes admit the re-signed spec.

pln bootstrap ssh fails

Symptom.

user@host failed (ssh: handshake failed) hint: for failed hosts, use `pln invite` and run `pln join --up <token>` on the remote host

Cause(s).

  • SSH access not set up. Bootstrap needs SSH as root or with passwordless sudo.
  • Target isn't Linux. Bootstrap-ssh is Linux-only.
  • Network blocks SSH. Firewall or VPN.

Fix. Test SSH directly: ssh user@host sudo -n true should succeed silently. If it doesn't, fix that first. As the hint suggests, you can always fall back to the out-of-band path:

pln invite --subject $(ssh user@host pln id) ssh user@host pln join --up <token>

Static site returns 404

Symptom. A site you published responds 404 instead of serving content.

Cause(s).

  • Static-HTTP not enabled on the node you're hitting. Sites are routed by Host header on each node's static-http listener. A node without that listener can't serve sites.
  • Spec hasn't reached this node yet. Possible right after publish; usually a couple of seconds.
  • Wrong Host header. The site name needs to match what you used when publishing.

Fix.

pln set # confirm static-http is set pln status static --include-offline curl -H "Host: my-site" -v http://localhost:8080/

If static-http isn't set, run pln set static-http and pln restart.

Properties don't seem to take effect

Symptom. You ran pln props or pln grant --prop but downstream policy decisions still use the old values.

Cause. Properties live in the grant, so a change re-issues the grant. Until the new grant reaches the relevant party, the old one is what admission sees.

  • For root: pln props updates the persisted file but doesn't re-issue the grant in-flight; restart to apply (pln restart).
  • For a delegated peer: pln grant issues immediately, but the new grant needs to gossip to whichever node is enforcing the policy. Usually a couple of seconds.

Fix. Restart root after pln props. For delegated peers, watch pln status nodes --wide until the new properties show on the affected node.

Last resort: nuke and start over

If a node's local state is wedged beyond reason and you don't mind losing it:

pln down pln purge --yes # wipes cluster state, preserves identity keys pln purge --yes --include-keys # wipes everything, including identity

Then re-init or re-join. --include-keys means the node will appear as a fresh identity to the cluster, so previous peers will refuse to talk to it without a fresh invite.

Still stuck

Open an issue with the symptom, the steps that produced it, and the relevant log excerpt at github.com/sambigeara/pollen/issues. Pollen is small enough that most issues get a fix or a workaround quickly.
