Concepts

Pollen's surface is small because the model underneath is small. A peer-to-peer mesh carries a gossiped CRDT that every node converges on. Your authority is a signed grant that keeps itself fresh while the root is offline. Published work outlives the publisher. Everything else on this page follows from those few ideas.

The mesh

Every node has an ed25519 identity. Peers maintain at most one QUIC connection between them, multiplexed for gossip, service tunnels, and seed traffic. mTLS is end-to-end; there are no shared secrets and no separate ingress.

Finding each other

Two peers learn about each other through gossip. Once they have exchanged addresses they try a direct UDP punch. Most of the time it works, even between two NATs. When it does not, they fall back to relaying through any mutually-reachable cluster node.

Peer A and Peer B are both behind NAT, and want to talk. 1. Exchange candidate addresses (via gossip or relay): A's addrs ---> B B's addrs ---> A 2. Simultaneous UDP punch: A: SYN ---> B B: SYN ---> A 3a. If either SYN escapes its NAT, the connection is direct. 3b. Otherwise both peers route through a public node R that they can each reach. R is just a normal cluster node that happens to be publicly reachable: A <----> R <----> B

A relay is just a regular node that happens to be publicly reachable. Bootstrap one with pln bootstrap ssh root@host --admin (or --publisher if it only forwards traffic) on a machine with a public IP, or hint it on start with pln up --public; the mesh verifies actual reachability via NAT probing. Public nodes' addresses are woven into invite tokens automatically, so a joiner behind NAT has a route in without you plumbing anything.

One transport, one connection

QUIC carries everything. Gossip messages, service tunnels, and seed RPCs share the same multiplexed stream per peer. Encryption is end-to-end; relays cannot read traffic they forward. There is no separate VPN, ingress controller, or sidecar.

See the recipe for adding a relay and the bootstrap-ssh reference.

Converged state

Every node holds the same document: a CRDT describing peers, services, workloads, sites, blobs, and the grant tree. CRDTs are designed so that any two nodes that have seen the same set of changes converge on identical state, regardless of the order they observed those changes.

That property gives Pollen three things for free:

  • No leader. No node is the source of truth. Every node can read; writes are gated by grant capability (publishers publish, admins also delegate); every node observes the same world.
  • Partition tolerance. Split the cluster in half and both sides keep working. Reunite them and the document re-converges.
  • Local decisions. Because every node has the same view, every node can make placement and routing decisions without consulting anyone else.
$ pln seed ./hello.wasm Node A writes one CRDT change: c1 = workloads[hello] := { hash: 4f3a, ... } Gossip rounds (anti-entropy) ensure every other peer eventually receives c1 via at least one path. Once converged, every node sees the same: state.workloads[hello] = { hash: 4f3a, ... }

Changes ride QUIC streams between peers. Conflict resolution is built into the document itself: each entry is keyed by a stable identifier and most fields are write-once or last-writer-wins. Tombstones mark deletes and propagate the same way as creates, so a peer that has been offline for an hour will catch up on both sides of the timeline when it reconnects.

There is no "control plane" to fail because there is no control plane at all. Every node holds it.

Grants: your authority, and how it stays fresh offline

A grant is a signed, gossiped, revocable credential. It says who a key is, what it may do, how much it may publish, and until when. Every grant traces back to the root key created by pln init, through a chain of delegations. A child grant can never hold more than the grant that issued it; that subset rule is enforced when the grant is minted and re-checked every time it is verified.

Three tiers

The ergonomic surface is three tiers. Pick the smallest that does the job.

  • Leaf (default): can call workloads and connect to services. Cannot publish, cannot delegate.
  • Publisher (--publisher): can publish workloads, services, blobs, and static sites. Cannot delegate further.
  • Admin (--admin): everything a publisher can do, plus admit and grant new peers. Only the root admin can mint other admins.

Under the tier the grant carries fine-grained per-kind publish capability (workloads, services, blobs, sites separately) and an optional count budget. Set the budget with --max-functions, --max-blobs, and --max-sites on pln invite at enrolment, or on pln grant for a connected peer; a tenant cannot publish more of a kind than its budget allows, and an unset budget means no limit.

[ root (admin) ] | | delegates | +---------------+---------------+ | | [ admin-A ] [ publisher-A ] | (CI box) | grants | +------+------+ | | [ publisher-B ] [ leaf-A ] role=engineer role=viewer team=backend team=ops

The grant tree lives on the gossiped CRDT, so every node can independently verify any grant. Revocation works through a deny set on the same document, and it is chain-aware: deny an admin and every grant whose chain runs through it fails at once, cluster-wide. The CRDT propagates a revocation the same way it propagates everything else.

Properties

Properties are key/value strings baked into a grant at issue time. Seeds see the caller's key and properties on every invocation, so authorisation, routing, and policy decisions can live inside workload code:

pln invite --prop role=engineer --prop team=backend
pln grant <peer> --prop tier=privileged
pln bootstrap ssh root@host --prop region=eu

The root node's own properties live in config.yaml and are re-applied on every pln up. Replace them with pln props. To see a single peer's tier, attributes, issuer chain, and the resources it publishes, use pln inspect <peer-id>.

The deadline is the stolen-key bound

A delegated grant carries a single hard deadline. The default is 30 days. It is the deliberate upper bound on how long a lost or stolen key stays usable: a grant cannot be extended by the key that holds it, only re-issued by an authority above it. Admin and infrastructure grants carry no deadline, because they are the few long-lived operators; the deadline exists to bound exposure for the many short-lived tenant identities. Within the deadline the grant renews itself without operator action; the next section is how.

Issue and scope grants with pln grant and pln invite. Revoke with pln deny.

Sessions: why nodes keep working with the root offline

Liveness is proved by a session: a short-lived token a node mints for itself, locally, by signing over its own held grant with its own key. Minting a session needs nothing but the grant already on disk and the node's private key. There is no network round-trip, so a node keeps authenticating to peers while the root and the node that issued its grant are unreachable. A session is bound to the connection key, so a copied credential cannot be replayed from a different key.

A session cannot outrun its grant's deadline. Within the deadline, sessions re-mint locally and indefinitely. The grant itself is renewed automatically before the deadline arrives:

  • A running daemon renews its grant in the background. It asks any reachable peer that holds delegate authority; it does not need the original issuer or the root to be online. The peer that renews re-clamps the grant to its own chain, so renewal can never widen authority or move the deadline out further than the chain allows.
  • A wire-mode context with no daemon renews opportunistically just before a command runs, once the grant has entered its renewal window. The window opens about a third of the way before the deadline, roughly 10 days out on the 30-day default, so a node gets many attempts before the deadline bites.

In normal operation you see nothing; renewal is silent. If renewal keeps failing while the grant is still valid, the node reports as degraded in pln status: still serving, flagged before a hard stop. If the deadline passes with no successful renewal, the node stops and logs that its grant is no longer valid. Recovery is to obtain a fresh invite from an admin and run pln join <token>. There is no pln renew command; renewal is never a manual step.

See Run with the root machine offline, inspect a context's deadline with pln context show, and read access expired or node degraded when it does not recover.

Admission: the four checks every publish passes

Every write into cluster state passes the same four checks, whether it arrived by gossip from another node or was made locally on this one. Local writes are not a fast path around the checks.

  • authenticate. The signature is genuine, the body matches its hash, and the publisher's grant chains to the root, is within its deadline, and is not revoked.
  • authorise. The grant actually carries the capability to publish this kind (workload, service, blob, or site), and the publisher satisfies its own policy clauses.
  • account. The publisher's count budget has room for one more of this kind. Re-publishing something it already holds costs no slot.
  • admit. The change merges into the CRDT and gossips on.

Runtime calls run the same authority rule plus policy on every invoke, fetch, or connect. A resource published with --public admits anyone through its gateway URL. Otherwise the caller's grant must be valid and match the resource's policy clauses, or the call is refused without revealing the resource shape so a denied caller cannot probe it.

Policy clauses

Every published resource can carry policy clauses. The runtime compares them against the caller's properties on every call.

seed(hello, --allow-prop role=admin) On every call, the runtime runs: for each --allow-prop clause on the resource: require caller's properties match exactly if any clause fails: close the stream silently So: leaf-A calls hello { role=engineer } -> deny (silent) leaf-B calls hello { role=admin } -> allow

Clauses are conjunctive: every --allow-prop on the resource must match. To express disjunction (editors or admins), mint both groups with a shared property and require it:

pln grant <editor> --prop tier=privileged
pln grant <admin>  --prop tier=privileged
pln serve 8080 ops --allow-prop tier=privileged

Pushing disjunction up to issuance keeps the runtime check fast (string equality across a few clauses, no expression evaluator on the hot path) and keeps policy auditable: who can call what is decided when the grant is minted, and the capable peers are visible from pln status nodes --wide. Without any policy flag a published resource is open to every authenticated peer in the cluster.

The check that fails tells you which stage rejected you. A forged or stale publish fails at authenticate. A grant that lacks the publish capability for a kind, or a property the policy requires, fails at authorise. A tenant over its count budget fails at account with an exhausted-budget message.

Recipes: Restrict who can call a workload and Cap what a tenant can publish. Symptoms: publish refused, call denied, budget exhausted.

What you can see

pln status answers one question: what does my authority let me see. The answer is projected through the caller's own identity, and it is the same whichever node you dialled.

  • An admin sees everything: every workload, site, blob, and every node in the cluster.
  • A tenant sees only its own workloads, sites, and blobs, and only the nodes that hold or run one of them. It never sees the serving node's view, other tenants' resources, or unrelated nodes.
  • An unidentified caller sees nothing.

A wire-mode tenant is not a mesh node, so its status header shows its own identity and its own grant's deadline, never the credential of the daemon it dialled. The serving node's identity is never the lens.

See the pln status and pln inspect references.

Workloads, sites and blobs

A seed is a unit of code that the cluster runs. Today that is a WebAssembly module compiled to Extism's plugin shape, which you can produce from Go, Rust, JavaScript, Python, C#, or Zig. pln seed publishes one as a signed record; the cluster handles everything else.

How replicas land somewhere

There is no scheduler. When a workload record gossips out, every node independently scores itself as a candidate host: does it have spare capacity? Does it already have the artefact in its content store? Is it close to where calls are originating? Each node decides locally whether to claim a replica, and how many.

$ pln seed ./hello.wasm --min-replicas 2 The record gossips out: hello, hash=4f3a, target=2 Every node independently scores itself as a candidate host: Node A: cpu 20% cache hit score 0.85 -> claim Node B: cpu 80% cache miss score 0.30 -> skip Node C: cpu 30% cache hit score 0.70 -> claim Two replicas land. No node was told what to do.

The scoring system tries to minimise call latency by placing replicas near the traffic that uses them. As load shifts, replicas migrate. Kill a node and the survivors notice its claims have gone stale; the next scoring round produces a new placement and brings the workload back to its target replica count.

Why they outlive you

A published workload, site, or blob does not carry a copy of the publisher's credential. It names its publisher, and the cluster resolves that publisher's grant from converged state at admission time. So a published resource keeps serving for as long as the publisher's grant is within its deadline and not revoked, even after the publisher has left the cluster entirely. Revoking the publisher, or any admin above it, invalidates everything it published cluster-wide on the next check, with no per-resource cleanup step.

Seeds calling seeds

A seed can invoke another seed in two ways:

  • Host call: pollen_request("pln://seed/upper/handle", input) blocks until the inner seed returns. The runtime picks a replica, ships the call, and hands the response back. Good for composition where the outer seed needs the result.
  • Tail call: the seed returns a JSON marker {"kind":"tail_call","uri":"pln://seed/upper/handle","input":"..."}. The runtime releases the caller's WASM instance immediately, routes the inner seed, and returns its output to the original caller. Good for fan-out and policy gateways where the outer seed has nothing more to do.

Storage and content addressing

Workload modules, static-site files, and named blobs are all just bytes. Pollen stores them in a single content-addressed store keyed by SHA-256, with each artefact's hash baked into the record that references it.

$ pln seed ./big.bin payload Publisher writes the bytes to its local content store: CAS[publisher] += { 4f3a... -> bytes } And gossips a blob record: blob(payload, hash=4f3a, publisher=...) Every other node now knows the blob exists. Any of them can stream it from any holder on demand, verifying the SHA-256 on arrival: Node B <------ stream over QUIC ------ Node A

Three things follow from content addressing:

  • Trust the bytes, not the source. Receivers verify the SHA-256 on arrival. A rogue peer cannot serve poisoned content under a known hash.
  • One-shot transfer. The same hash from any holder is the same bytes. Two peers can each pull from a third without coordination.
  • Free deduplication. Two seeds that share an artefact share one entry in the store.

Blobs are encrypted at rest. Each blob carries a fresh AES-256-GCM data key, and every recipient gets that key wrapped to their identity key. A node's disk holds only ciphertext plus the wrappings addressed to it, so losing the disk leaks nothing.

Reading a blob

Because the on-disk form is ciphertext, you cannot cat a blob out of the store. pln fetch is the export path: it streams plaintext bytes from a holder and writes them to the path you give. The local store is not touched, and the fetcher never holds an encrypted copy on disk. To host a copy on this node, use pln seed.

Eviction

When a resource is unseeded, its hash becomes a tombstone in the gossip layer. Holders that do not see any other live record referencing the hash drop it from their store on the next sweep. There is no explicit GC step.

Routing to the nearest copy

Who may publish a thing and where its bytes physically live are separate questions. The set of nodes holding a copy is tracked per resource, and it carries locality. A fetch or a call is served from the nearest holder by network coordinate, not from wherever the resource was first published, so a geographically spread cluster stays fast.

When you call a seed, the local node picks two candidates (power-of-two-choices) and routes to whichever responds with the lower load score. Distance ties break deterministically by peer key, so repeated fetches keep hitting the same warm copy. Placement and call routing share the same nearest-holder choice, so a blob fetch and a workload invocation agree on what "nearest" means.

The same model handles services: a seed can call pln://service/<name> to reach a TCP or UDP service somewhere on the mesh, with the same routing and the same admission checks as seed-to-seed calls.

Staying current

The CLI and the daemon negotiate a protocol version range when they connect. If their ranges do not overlap, the side that is behind is told so explicitly, with the action to take. There is never silent misbehaviour on a mismatch.

  • pln is behind: pln is out of date: this daemon speaks protocol X-Y but pln supports only up to Z; upgrade pln. Upgrade the pln binary.
  • The daemon is behind: the daemon is out of date: it speaks protocol X-Y but pln requires at least Z; upgrade the daemon. Upgrade the daemon.
  • The daemon predates negotiation entirely: the daemon is out of date: it does not support protocol negotiation; upgrade the daemon.

Upgrade either side with the upgrade recipe; see also client or daemon out of date.

How the pieces fit

A single pln seed exercises the whole stack:

  1. The CLI hashes the artefact and stores it in the local content store.
  2. The supervisor signs a record with the local grant; the record carries the hash, any policy clauses, and the publisher's identity by key.
  3. The change enters the CRDT and passes the four admission checks on every node that receives it, by gossip or locally.
  4. Each peer scores itself as a candidate host. Selected peers fetch the artefact from the nearest holder over QUIC, verifying the hash on arrival.
  5. The first call routes to whichever replica is nearest and least loaded. The runtime checks the caller against the resource's policy. If it passes, the call goes through.

No central coordinator was contacted. No shared secrets were used. Every step was decided locally against the same converged view of the world.

The other commands, pln serve, pln connect, pln invite, pln grant, pln deny, exercise the same machinery with different payloads. Once you have understood seeds, the rest of the surface follows.
